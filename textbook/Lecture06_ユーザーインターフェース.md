# 第6回：ユーザーインターフェース

---

## 1. ユーザーインターフェース（UI）とは何か

ユーザーインターフェース（UI）は、プレイヤーとゲームの内部処理（コアメカニクス）の間に位置し、ゲームを「見える・聞こえる・操作できる」ものにする仕組みである。UIの出来はプレイヤーがゲームに対して「満足か失望か」「楽しいか苛立たしいか」を判断する最大の要因の一つとなる。

UIの役割は大きく分けて3つある。

1. **入力の変換**：プレイヤーのボタン操作などの現実世界の行動を、インタラクションモデルに基づいてゲーム世界の行動に翻訳し、コアメカニクスに渡す。
2. **情報の提示**：コアメカニクスの内部データのうち、プレイヤーが必要とする情報を視覚・聴覚で提示する（フィードバック）。
3. **体験の創出**：単に情報を全て見せるのではなく、ゲームプレイとストーリーテリングの「体験」として適切にフィルタリングする。

### 用語の整理

| 用語 | 意味 |
|------|------|
| **視覚要素** | 画面上に表示される情報（メインビュー、インジケータ等） |
| **音声要素** | 効果音、環境音、音楽、台詞など |
| **制御要素** | プレイヤーの入力を受け付ける仕組み（ボタン、メニュー等） |
| **フィードバック要素** | プレイヤーの行動結果や状態を伝える視覚・聴覚要素 |
| **コントローラボタン** | 入力デバイス上の物理ボタン |
| **スクリーンボタン** | 画面上に表示され、マウスでクリックするボタン |

> **設計上の注意**：コアメカニクスを設計する際は、特定の入出力デバイスの性能に依存しない設計にすべきである。UIにハードウェア管理を任せ、コアメカニクスはハードウェア非依存に保つ。こうすれば移植時にUIだけを再設計すればよい。

**キーポイント**
- UIはプレイヤーとゲーム内部の「橋渡し役」であり、入力変換・情報提示・体験創出の3機能を持つ
- コアメカニクスはUI・ハードウェアから独立させて設計する

## 2. プレイヤー中心のインターフェースデザイン

ゲームのUIは一般的なソフトウェアのUIと異なり、プレイヤーに全ての情報を見せたり最大限の制御を与えたりするものではない。ゲーム体験として楽しいものにするために、情報と操作を適切に「媒介」する必要がある。

### 不要なイノベーションを避ける

> **デザインルール**：標準が存在するなら、それを使え。既に実績のある操作体系があるのに、独自UIを無理に導入すると、プレイヤーは不慣れな操作に苛立ち、他にどれほど良い点があってもゲームを嫌いになる。

同ジャンルの優れたゲームを研究し、長年進化してきた標準的なフィードバック要素と操作方式を採用すべきである。もし新しいUIを導入するなら、チュートリアルレベルを作り、初心者と経験者の両方で徹底的にテストすること。

### 一般原則

| 原則 | 説明 |
|------|------|
| **一貫性** | 同じ機能には同じボタン・メニュー項目を割り当て、色・書体・レイアウトを統一する |
| **適切なフィードバック** | ボタン操作には即座に反応を返す。非活性ボタンでも音で応答する |
| **プレイヤーが主導権を持つ** | アバターを勝手に動かさない。プレイヤーは自分が操作している感覚を求めている |
| **操作ステップの最小化** | 特殊技は最大3ボタン。メニュー階層は浅く保つ |
| **操作の取り消し** | ゲームバランスに影響しない限り、アンドゥを許可する |
| **身体的負荷の軽減** | 頻繁な操作はアクセスしやすいボタンに割り当てる |
| **短期記憶への配慮** | 常時必要な情報は常に表示。暗記を強制しない |
| **関連情報のグループ化** | 関連するフィードバックと制御を画面上でまとめる |
| **経験者向けショートカット** | メニューの頻出コマンドにはキーボードショートカットを用意する |

### プレイヤーが知るべきこと

UIを設計する際は、「プレイヤーが問いかけるであろう質問」を基準に考える。

- **今どこにいる？** → メインビュー＋ミニマップ＋環境音
- **今何をしている？** → アバターの動作表示＋適切な動作音
- **どんな課題に直面している？** → メインビューでの課題表示
- **行動は成功した？失敗した？** → アニメーション＋効果音
- **必要なリソースはある？** → 弾薬・資金・エネルギー等のインジケータ
- **敗北の危険はある？** → HP・残り時間のインジケータ＋警告音
- **進捗はどうか？** → スコア・達成率・チェックポイントの表示
- **次に何をすべきか？** → ヒントや目標リスト
- **結果はどうだった？** → レベルクリア時のスコア画面・報酬演出

> **デザインルール**：負けたプレイヤーを嘲笑してはならない。プレイヤーは負けて既に落胆している。共感がプレイヤー中心設計の根幹にある。

**キーポイント**
- 標準UIを尊重し、不要なイノベーションを避ける
- 9つの一般原則（一貫性、フィードバック、主導権等）を遵守する
- 「プレイヤーの問い」を基準にフィードバック要素を設計する

## 3. デザインプロセス

UIデザインは、ゲームデザインの「詳細化（elaboration）」段階の初期に行う。コンセプトフェーズが完了する前にUI設計を始めると、全体設計の変更でやり直しになるリスクがある。

### ステップ1：ゲームプレイモードの定義

ゲームプレイモードとは、カメラモデル＋インタラクションモデル＋利用可能なゲームプレイ（課題と行動）の組み合わせである。

- **主要モード**を最初に設計する（プレイヤーが最も長い時間を過ごすモード）
- 次に他のモード（ストーリー配信、対話、ポーズメニュー等）を設計する
- モード間の構造を**フローボード**で計画する
- モード間で共通するUI要素を統一する

### ステップ2：画面レイアウトの選択

メインビュー（ゲーム世界の表示）が画面上最大の要素であるべきである。メインビューの配置方法には2種類ある。

- **ウィンドウ方式**：画面の一部にメインビュー、周囲にフィードバック・制御パネル
- **フルスクリーン＋オーバーレイ方式**：メインビューが画面全体を占め、UI要素がその上に重なる

### ステップ3：情報の提示と操作の設計

1. プレイヤーに常時見せるべき情報を選定し、適切なフィードバック要素を選ぶ
2. プレイヤーの全行動に対して制御方式を設計する
3. 入力デバイスへのマッピングを行う

### プロトタイプの構築

経験豊富なデザイナーは、最終仕様を書く前に必ずUIプロトタイプを構築しテストする。プレースホルダーのアートや音を使い、メニュー遷移やボタン応答を確認する。一度に全部作るのではなく、少しずつ構築・テスト・調整を繰り返す。

**キーポイント**
- UIデザインは詳細化段階の初期に行う
- 主要ゲームプレイモードから設計を始め、他モードへ展開する
- プロトタイプの反復的な構築・テストが不可欠

## 4. 複雑さの管理

ゲームが高度化するにつれ、UIも複雑化する。複雑さを管理しなければ、プレイヤーはオプションを覚えきれず、画面が制御要素であふれてメインビューの余地がなくなる。

### ゲームの簡素化

- **抽象化**：詳細な要素を簡略化または削除する（例：燃料消費をシミュレーションしない → 燃料ゲージが不要になる）
- **自動化**：プレイヤーの制御から外し、コンピュータに任せる（例：オートマチック変速 → 初心者モード/上級者モードで切替可能にする）

### 深さ vs. 広さ

- **広いUI**：多くのオプションを同時に表示。学習コストは高いが慣れると効率的（例：航空機のコックピット）
- **深いUI**：階層メニューで少しずつ選択肢を提示。学習コストは低いが操作に時間がかかる

理想的には両方を提供する。初心者向けの深いUI（メニュー）と、経験者向けの広いUI（ショートカットキー）を併用する。階層は最大3〜4段に抑え、頻繁に使う機能は1〜2ステップでアクセスできるようにする。

### コンテキスト感応型インターフェース

現在の文脈で無意味なオプションを非表示にすることで複雑さを軽減する。例えば、マウスポインタをオブジェクトに向けると可能な操作に応じて形状が変わる（木に向けると斧の形になる等）。

### 曖昧さの回避

UIが正しく機能し見た目も良くても、ボタンやメニューの意味がわからなければ問題である。以下に注意する。

- **アート偏重**：美しいが意味が伝わらないUI要素
- **省スペースへの過度な圧縮**：小さすぎるアイコンは区別がつかない
- **開発者の慣れ**：自分が作ったものの分かりやすさは自分では判断できない。必ず第三者にテストさせる

**キーポイント**
- 抽象化・自動化でゲーム自体を簡素化するのが最優先
- 深い（メニュー型）と広い（一覧型）のUIを併用し、初心者と経験者の双方に対応する
- コンテキスト感応で不要な選択肢を隠し、第三者テストで曖昧さを排除する

## 5. インタラクションモデル

インタラクションモデルとは、プレイヤーの入力とゲーム世界での行動の関係を定義するものである。

| モデル | 説明 | 例 |
|--------|------|-----|
| **アバター型** | 一人のキャラクター（アバター）を操作。アバターの周辺のみ影響を与えられる | アクションゲーム、FPS |
| **マルチプレゼント型** | ゲーム世界の複数箇所に同時に働きかけられる。俯瞰カメラが必要 | チェス、RTS |
| **パーティ型** | 小グループをまとめて操作。ポイント＆クリック＋俯瞰視点が多い | RPG |
| **出場者型** | 質問に回答し決定を下す。ナビゲーション不要 | クイズゲーム |
| **デスクトップ型** | PCデスクトップを模倣。オフィス系のゲームに限定 | 経営シミュレーション |

既存のモデルに収まるデザインが望ましい。独自モデルを作る場合は、操作を教えるための詳細なチュートリアルが必要になる。

**キーポイント**
- インタラクションモデルは5つの基本型がある
- 標準的なモデルを採用することで学習コストを低減できる

## 6. カメラモデル

カメラモデルは、プレイヤーがゲーム世界をどのように見るかを定義する。映画のカメラになぞらえ、「仮想カメラ（virtual camera）」がゲーム世界を映すものとして設計する。

### 3D vs. 2D

2Dグラフィックスでは一人称・三人称視点は使えない。3Dグラフィックスの方が表現力は高いが、ツール・スキル・時間が不足しているなら、見栄えの良い2Dの方が見栄えの悪い3Dより常に望ましい。

### 一人称視点（First-Person Perspective）

アバターの目線に固定されたカメラ。アバター自体は通常見えない。

| 利点 | 欠点 |
|------|------|
| アバターのアニメーション開発コスト削減 | アバターの外見カスタマイズの楽しみがない |
| カメラAIが不要 | アバターのボディランゲージが見えず個性が伝わりにくい |
| 照準が直感的 | 映画的カメラアングルによる演出ができない |
| 環境との相互作用が容易 | ジャンプなどの体操的動作のタイミングが取りにくい |
| | 急な回転で酔いを引き起こしやすい |

### 三人称視点（Third-Person Perspective）

アバターの背後上方からカメラが追従する。アバターが見えるためキャラクター表現に優れるが、カメラ制御の設計課題が多い。

**カメラの回転挙動**（アバターが向きを変えた時）：
- 常にアバターの背後に追従 → 速い回転で酔いの原因になる
- 数秒遅れてゆっくり追従 → バランスが良い（Super Mario 64方式）
- アバターが止まった時のみ追従 → 後退時に前方が見えない問題がある

**障害物の問題**：アバターが壁際に立つとカメラが壁の向こう側に行ってしまう。対策として、壁を半透明にする、カメラを上方に移動する、アバターの頭を半透明にする等の手法がある。

### 俯瞰視点（Aerial Perspectives）

パーティ型やマルチプレゼント型のインタラクションモデルで使用される。

- **トップダウン視点**：真上から見下ろす。地図的で親しみやすいが、建物の屋根と人の頭頂部しか見えない
- **アイソメトリック視点**：斜め30度から見下ろす2D表示。建物の側面も見え、没入感が高い
- **自由カメラ（Free-roaming）**：3Dエンジンによる俯瞰。上下移動・回転・ズームが自由にでき、遠近法も正確
- **コンテキスト感応カメラ**：場面に応じて自動的に最適なアングルに切り替わる。映画的演出に優れるが実装コストが高く、高速アクション中に突然視点が変わるとプレイヤーを混乱させる

> **デザインルール**：激しいアクション中はカメラを予期せず動かしてはならない。固定的で予測可能な視点を使うこと。

![カメラモデルの例](images/img_p245_00.jpeg)

**キーポイント**
- カメラモデルはインタラクションモデルと密接に関連する
- 一人称は没入感が高いが制約も多く、三人称はキャラ表現に優れるがカメラAIの設計が必要
- 俯瞰系は自由カメラが現代の主流。コンテキスト感応カメラは演出力が高いが設計負荷が大きい

## 7. 視覚要素

### メインビューの表示方式

| 方式 | 特徴 |
|------|------|
| **ウィンドウ表示** | メインビューを画面の一部に配置。情報量は多いが没入感が低下 |
| **不透明オーバーレイ** | メインビュー全画面表示の上にUI要素を重ねる。消えた時の視界が広い |
| **半透明オーバーレイ** | 背景が透けて見えるが、テキスト表示には不向き（背景と文字が混ざる） |

### フィードバック要素（インジケータ）

プレイヤーにゲームの内部状態を伝える視覚要素。ゲームのテーマに合ったものを選ぶ。

| 種類 | タイプ | 説明 | 例 |
|------|--------|------|-----|
| **数字表示** | 一般数値 | 大きな数値を省スペースで表示。一瞬の判読には不向き | スコア、弾薬数 |
| **針ゲージ** | 一般数値 | 一目で読めるが画面占有が大きい | 速度計、タコメーター |
| **パワーバー** | 一般数値 | 棒グラフ状。緑→黄→赤で危険度を直感的に伝達 | HP、残り時間 |
| **小さな繰り返し** | 小整数 | アイコンの個数で残数を表示（最大5つ程度） | 残機、手榴弾 |
| **色つきライト** | 記号 | 数ピクセルで二値・三値を表示 | オン/オフ状態 |
| **アイコン** | 記号 | 少数の選択肢を小スペースで表現 | 季節、状態異常 |
| **テキスト** | 記号 | 抽象概念を表現可能。ただしローカライズコストが高い | アドバイザーの助言 |

### ミニマップ

ゲーム世界のミニチュア版。2種類の表示規約がある。

- **ワールド指向**：世界全体を北を上にして表示。現在のメインビュー範囲を矩形で示す
- **キャラクター指向**：アバターを中心に据え、アバターの向きが常に上。レーダースクリーンとも呼ばれる

### キャラクターポートレート

俯瞰視点で顔が見えにくい時に小ウィンドウで表情を表示する。Doomのアバターポートレートは被ダメージに応じて血まみれになり、HPフィードバック要素としても機能した。

### テキストとローカライズ

- テキストは画像に埋め込まず、必ずテキストファイルに分離して管理する
- 最小文字高は12ピクセル（日本語は16ピクセルが望ましい）
- 全て大文字のテキストは読みにくく、SHOUTING（叫び）に見える。警告時のみ使用する

![UIの視覚要素例](images/img_p259_01.jpeg)

**キーポイント**
- メインビューを最大要素とし、フィードバック要素は目的に応じた形式を選択する
- ミニマップはワールド指向とキャラクター指向の2種がある
- テキストは画像から分離し、ローカライズを前提に設計する

## 8. 音声要素

### 効果音

ゲーム世界の行動や出来事に対応する音。UIのスクリーンボタンにもクリック音などの聴覚フィードバックを付与すべきである。危険の接近を音で先に知らせる映画的手法も有効である（足音、銃のコッキング音等）。

### 振動（ランブル）

コントローラの振動機能は、爆発などの大きなイベントや壁への衝突などの否定的イベントに使う。常用するとプレイヤーが無視するようになり、手にしびれが生じる。

### 環境音

メインビューが「ここはどこか」を視覚で伝えるように、環境音は聴覚で伝える。都市の交通音、ジャングルの鳥の声などである。一人称・三人称ゲームでは**ポジショナルオーディオ**（音源の空間的位置を再現する立体音響）を使うべきである。

### 音楽

音楽はゲームのトーンとペースを設定する。文化的メッセージが強いため、テーマとの整合に注意する。長時間の繰り返しに耐えられる楽曲を選び、ダイナミックレンジの広い曲は避ける。**アダプティブミュージック**（ゲーム状況に応じて動的に変化する音楽）や**レイヤリング**（複数の楽曲を同時に異なるボリュームで合成）などの技法がある。

### 台詞とナレーション

- 繰り返される台詞はすぐに飽きられるため、同じ内容に複数のバリエーションを用意する
- 脚本と演技の質は極めて重要。下手な声優は即座に没入感を破壊する

> プレイヤーは音楽・効果音・会話の音量を個別に調整できるようにすべきである。

**キーポイント**
- 効果音はUI操作にも付与し、音で危険を先行告知する
- 環境音とポジショナルオーディオで空間認識を支援する
- 音楽はテーマとの整合性を保ち、繰り返し耐性を確保する

## 9. 入力デバイス

ゲームに同梱される標準的な入力デバイスに対して設計すべきであり、特殊なデバイスを前提にすると市場が限定される。

### デバイスの分類

| 分類軸 | 種類 | 説明 |
|--------|------|------|
| **データ型** | バイナリ / アナログ | オン・オフのみ / 連続値 |
| **次元** | 1D / 2D / 3D | 送信するデータの数 |
| **値の種類** | 絶対値 / 相対値 | ニュートラル位置からの距離 / 前回位置からの移動量 |

### 主な入力デバイス

| デバイス | 次元 | データ型 | 特徴 |
|----------|------|----------|------|
| **コントローラボタン/キー** | 1D | バイナリ | 単発・連射・継続の3つの使い方がある |
| **感圧ボタン** | 1D | アナログ | 押す強さで値が変わる |
| **D-pad** | 2D | バイナリ | 8方向のみ。粗い制御 |
| **ジョイスティック** | 2D | アナログ | 細かい操舵に最適。自動復帰するため精密ポインティングには不向き |
| **マウス** | 2D | 相対アナログ | 精密な位置指定。無限の移動範囲。ニュートラル位置がない |
| **タッチスクリーン** | 2D | 絶対アナログ | 直感的だが長時間使用で指が疲れる |
| **加速度センサー** | 3D | アナログ | コントローラの動き・傾きを検出（Wiiリモコン等） |
| **GPS** | 3D | 絶対値 | 屋外の位置情報。拡張現実ゲームに使用 |

**キーポイント**
- 標準同梱デバイスを前提に設計する
- デバイスの次元・データ型・値の種類を理解し、ゲームの操作に最適なものを選択する
- マウスは精密操作に優れ、ジョイスティックは操舵に最適と、それぞれ得意分野が異なる

## 10. ナビゲーションメカニズム

ナビゲーションメカニズムは、プレイヤーの操作入力とアバターの画面上の動きの関係を定義する。この関係は一貫性と予測可能性が極めて重要であり、突然のカメラアングル変更などは操作ミスの原因となる。

### 画面指向ステアリング

ジョイスティックを上に倒すとアバターが画面上方に移動する方式。

- **トップダウン/アイソメトリック**：上下左右がそのまま画面の上下左右に対応（最もシンプル）
- **サイドスクロール**：左右で移動、ジャンプは別ボタン
- **3D（Crash Bandicoot方式）**：上で画面奥へ、下で手前へ。サイドスクローラーに奥行きを加えた感覚

### アバター指向ステアリング

ジョイスティック上でアバターが「現在向いている方向」に前進する方式。一人称ゲームでは唯一の選択肢。

- **ジョイスティック/D-pad**：上＝前進、下＝後退、左右＝回転（移動はしない。斜め入力で回転＋前進）
- **マウス＋キーボード（FPS標準）**：マウスで視線方向を制御、WASD（またはIJKL）キーで移動。ストレイフィング（横移動）が可能

### 飛行

3次元移動には2Dデバイスでは足りないため、追加デバイスが必要。

- **固定翼機**：ジョイスティックでピッチ・ロール、スロットル（スライダー/キー）で速度
- **ヘリコプター**：ジョイスティックで回転・前後移動、別コントロールで上昇・下降
- **宇宙船**：固定翼機と同様だが、左右でヨー（水平回転）する場合もある

### ポイント＆クリックナビゲーション

俯瞰視点やコンテキスト感応カメラで使用。プレイヤーが目的地をクリックするとアバター/ユニットがパスファインディングで自動的にそこへ移動する。RTSやパーティ型RPGで多用される。ウェイポイント（中間目標点）を設定できるようにすると、プレイヤーが経路をある程度制御できる。

**キーポイント**
- 画面指向とアバター指向の2大方式があり、カメラモデルに合わせて選択する
- FPSではマウス＋キーボードによるアバター指向ステアリングが標準
- 俯瞰視点ではポイント＆クリック＋パスファインディングが効果的

## 11. カスタマイズ

プレイヤーが入力デバイスを自分好みに設定できる機能は、設計コストに対して効果が非常に高い。

### 必須のカスタマイズ機能

- **マウスボタンの左右入替**：左利きプレイヤーへの対応
- **マウス/ジョイスティックの上下反転**：上で見上げ or 上で見下ろしの好みに対応
- **キー/ボタンのリマッピング**：プレイヤーが好みのキー配置に変更できる機能。必須アクションが未割当のまま終了しようとした場合は警告する
- **音量の個別調整**：音楽・効果音・音声をそれぞれ独立して調整可能にする

### 自由度の原則

同じ次元・同じデータ型を持つデバイス間であれば、基本的にプレイヤーが相互に入れ替えられるようにすべきである。ただし、自動復帰の有無や移動範囲の制限が異なるデバイス間では、一部の機能や利便性が失われることがある。

**キーポイント**
- カスタマイズ機能は低コストで高い満足度をもたらす
- マウスの左右入替、上下反転、キーリマッピングは必須機能として実装する

## 本講のまとめ

1. **UIの本質**：プレイヤーとゲーム内部の媒介であり、体験を創出するもの
2. **プレイヤー中心設計**：標準を尊重し、9つの一般原則を守り、プレイヤーの問いに答える
3. **デザインプロセス**：モード定義 → レイアウト → フィードバック/制御設計 → プロトタイプ
4. **複雑さの管理**：抽象化・自動化・深さと広さのバランス・コンテキスト感応
5. **インタラクションモデル**：アバター型・マルチプレゼント型・パーティ型・出場者型・デスクトップ型
6. **カメラモデル**：一人称・三人称・俯瞰（トップダウン/アイソメトリック/自由カメラ/コンテキスト感応）
7. **視覚要素**：メインビュー方式、インジケータの種類、ミニマップ、テキスト設計
8. **音声要素**：効果音・振動・環境音・音楽・台詞の設計原則
9. **入力デバイス**：次元・データ型・値の種類で分類し、操作に最適なデバイスを選ぶ
10. **ナビゲーション**：画面指向/アバター指向/ポイント＆クリックの3方式
11. **カスタマイズ**：低コスト高効果。キーリマッピングと入力反転は必須
